# Spec · 画布：参与方选择器 + 单一「保存」

> 来源：用户 2026-10-12 提的两个 bug（原话）
> 1. 「loomerto canvas 视图中，在做选项框不能下拉选择当前所有的参与者」
> 2. 「保存字段按钮和该状态按钮含义重复，去掉改状态按钮」
>
> 状态：**待实现（ready-for-agent）**。本文档由 `to-spec` 模板合成，不含访谈。
> 需求条目号在实现时并入 `REQUIREMENTS.md`（见 §7）。

---

## 1. Problem Statement

用户在一块**可编辑画布**（`loomerto open <plan 数据文件>`，实现 = `loomerto/serve.py` +
`loomerto/assets/canvas.html`）上给块改字段时，撞到两件事：

**① 「在做（`--by`）」这个选项框选不出当前的参与者。**
用户在「在做」框里想选一个已经登记在计划里的参与方，但下拉里没有他要的人（或者干脆一个候选都没有）。
结果是：这个框只能靠手打 id，打错了没人拦 —— 而 `--by` 正是「谁在做」的唯一记录位（R-01），
写错了三视图里的线程归属就跟着错。

**② 「保存字段」与「改状态」两个按钮语义重复。**
右栏底下并排三个按钮：`保存字段` / `改状态` / `打回重做`。前两个覆盖的范围**大面积重叠**
（都带认领人、判据），用户得先猜「我这个改动该按哪个」，按错了还有一部分改动被**静默丢掉**：

- `保存字段`（`op=edit`）只改 标题 / 做什么 / 判据 / 认领人 / 类型，**不动状态**；
- `改状态`（`op=status`）改状态 + 认领人 + 判据，但**静默忽略标题 / 做什么 / 类型** ——
  用户在框里改了标题、再点「改状态」，标题的改动就没了（下面 §3 有实测）。

用户的诉求很直接：**去掉「改状态」这个按钮**，别让同一个动作有两个入口。

---

## 2. Solution（用户视角）

1. **「在做」与「认领人」都变成真正可选的下拉**，候选 = 这份计划里所有**能当参与方用的人**：
   注册在 `plan.json` 的 `participants`，**加上**计划里实际已经出现过的认领人 / 在做的人
   （否则当前认领人自己都选不到 —— 这是本 bug 的主因，见 §3）。候选里显示人类看得懂的名字，
   不只是 id。新建块 / 新建任务表单里的「认领人」同样可选。
2. **右栏只留一个保存动作**：一个「保存」按钮，把你在这一屏里改的**所有东西**（字段 + 状态）
   一次写回。「打回重做」作为独立语义保留（它不是「保存」，是「送回原认领人重做」）。
   不会再出现「改了标题却因为点的是另一个按钮而丢掉」。

## 3. 实测证据（本次复现，非推断）

用 checkout 起 `python3 -m loomerto --plan <文件> open --port N`，在真 Chrome 里读 DOM 得到：

**Bug ① 三个独立缺陷**

| # | 缺陷 | 证据（实测） |
|---|---|---|
| 1a | 候选**只取 `participants`**，不含计划里实际用到的 owner/`exec.by` | `~/.hermes/workspace/plans/skillweave` 的 `participants = ["you"]`，但 44 个块的 `owner = "default"`；页面里 `#f_owner.list.options = ["you"]` ⇒ **当前认领人 default 选不到**，只能手打 |
| 1b | 新建块 / 新建任务表单的「认领人」挂着 `list="people"`，**页面里没有那个 datalist** | `newBlockForm()` 后：`#n_owner.list === null`（`resolves:false`），`document.querySelectorAll('datalist').length === 0` ⇒ 点了完全不弹 |
| 1c | 候选只给 `id`，不给 `label` | `#people` 的 option：`value:"stronghold"`、`textContent:""`；而 `VIEW.participants` 里同一个人的 `label:"Stronghold3369"` ⇒ 下拉里只有 id，认不出是谁 |

> 1a 的对照：`dream-waveA` 那份 `participants = ["stronghold","default","you"]`，三个块的 owner 都在名单里，
> 于是下拉**能**列出 3 个 —— 所以这个 bug 不是「datalist 不工作」，而是**候选来源太窄**，
> 只在「owner 没登记成 participant」的真实计划上才暴露（实测 8 份真实 plan 里，`skillweave` 一份
> 就有 **44 处** owner 不在 participants 里）。

**Bug ② 两个按钮的覆盖范围与静默丢弃**

同一块（`T-001#B-001`）跑两次请求：

| 动作 | 前端发的 op | 结果（实测 HTTP 200） |
|---|---|---|
| 保存字段 | `edit` + 全字段 | `改了 标题、做什么、类型、认领人、判据` —— **`raw_status` 不变**，`exec.by` 不变 |
| 改状态 | `status` + 全字段 | `done → running` —— 状态、认领人、判据生效；**`title` / `doc` / `kind` 的改动被静默丢弃**（`edits.set_status` 根本不收这三个键） |

即：两个按钮的并集才是「用户以为自己保存的东西」，交集让人困惑，差集让人丢改动。

## 4. User Stories

**参与方下拉（Bug ①）**

1. 作为画布使用者，我想在「在做（`--by`）」里下拉选到**所有**参与方，这样我不必手打 id、也不会打错。
2. 作为画布使用者，我想在「认领人」里下拉选到所有参与方，这样派活是一下点选，不是一次拼写。
3. 作为接手一份**没登记全 participants** 的计划的人，我想下拉里至少能看到**这份计划里实际出现过的人**，
   这样我不用先去改 `plan.json` 才能给自己派活。
4. 作为使用者，我想下拉里显示**人的名字**（label），而不只是 `id`，这样我一眼认得出是谁。
5. 作为使用者，我想在**新建块**表单里也能下拉选认领人，这样新建时就不必手打。
6. 作为使用者，我想在**新建任务（泳道）**表单里也能下拉选认领人，同上。
7. 作为使用者，我希望下拉候选**不重复**（同一个人只出现一次），且**顺序稳定**（同一份计划每次打开一样）。
8. 作为使用者，我想在候选里能分清「已注册的参与方」与「只是出现过的人」，这样我知道该不该去补登记。
9. 作为使用者，我希望能**自由输入**一个还没出现在计划里的人（下拉是建议，不是白名单），
   这样临时拉个人进来不必先改数据。
10. 作为使用者，当我在「在做」里选了一个人、而当前状态不收 `--by` 时，我想看到**一句人话**说明为什么不行，
    而不是一个看不懂的报错或静默失败。

**单一保存（Bug ②）**

11. 作为使用者，我想右栏只有**一个保存按钮**，这样我不用猜该点哪个。
12. 作为使用者，我想一次保存就写回**我改过的所有东西**（标题 / 做什么 / 判据 / 认领人 / 类型 / 状态），
    这样不会有改动被静默丢掉。
13. 作为使用者，我想「状态」仍然是**下拉**（含送审 / 打回 / 收工），这样改状态还是点一下的事。
14. 作为使用者，我想改状态时**状态机语义不变**：记一条 run、在途状态登记「谁在做」、收工/取消清掉线程登记、
    从「待评审」走出去且不是「已完成」时把说明落进 `feedback`。
15. 作为使用者，我想「打回重做」仍然是一个**独立按钮**（它的 note 语义与普通保存不同），
    这样我打回时不必先把状态改成「已认领」再保存。
16. 作为使用者，我想保存**只改我真的动了的东西** —— 没动过的字段不该因为一次保存而被重写或记进日志。
17. 作为使用者，我想在什么都没改就点保存时得到**一句提示**（「没有变化」），而不是一次假的成功。
18. 作为使用者，我想保存失败时**什么都不写**（状态非法 / 会成环 / rev 过期），这样我不会得到一个半改的数据。

**纪律与不回归**

19. 作为包维护者，我想这次改动**不新增第二份实现**：字段写入仍走 `edits.edit_block` / `edits.set_field`，
    状态写入仍走 `edits.set_status`（`edits.py` 是唯一实现），这样 CLI 与画布不会漂。
20. 作为包维护者，我想一次保存仍然是**一次 `store.commit()`**（json + 三视图同步一次），
    这样不会出现「json 改了、md 没跟上」。
21. 作为包维护者，我想这次改动**不动 `plan.json` 的结构**（不加新键、不改 schema），
    这样老计划不用迁移。
22. 作为包维护者，我想**命令层 CLI 完全不受影响**（`block set_status` / `block set_title` … 行为与输出不变），
    这样这次只是前端与一个 op 的改动。
23. 作为包维护者，我想 `docs/canvas-sync.md` 的协议表（op 列表）**与实现一致**，这样接第二个前端的人不会被误导。
24. 作为包维护者，我想画布与只读看板 `plan.html` **共用同一份主题**（`theme.css`），
    这样两页不会各长一套观感。
25. 作为包维护者，我想这次改动**只绑 127.0.0.1、纯 stdlib、零依赖、`>=3.9`** 这些硬约束不变。

## 5. Implementation Decisions

> 下面是本次拍板/建议的实现决定。**未获用户确认的项已标「假定」**，实现时可被推翻。

### 5.1 参与方候选（Bug ①）

- **候选集合 = `participants` ∪ 计划里实际出现的 `owner` ∪ 计划里实际出现的 `exec.by`**，
  按 id 去重。（**假定**：用户未答，取推荐项。理由：这是 1a 的唯一解 —— 只放宽到 participants
  就修不掉「当前认领人选不到」。）
- **候选由服务端算好发下来**，不在前端拼：`GET /api/plan` 的 `view` 里给一份
  `participant_options`（或等价字段），每项带 `id` / `label` / `kind` / 一个「是否已注册」的标记。
  理由：与「派生一律由 Python 侧 `model` 算」（`docs/canvas-sync.md` §1）一致，
  前端不重新实现一遍规则。**注意**：`view.participants`（原样透传）保留不动，避免破坏已有前端。
- **三个字段都用同一份候选**：编辑器的 `认领人` / `在做`，以及新建块 / 新建任务表单的 `认领人`
  （**假定**：用户未答，取推荐项 —— 1b 是独立的真 bug，不修则新建表单仍然弹不出）。
- **新建表单的 datalist 必须真的渲染进 DOM**：现在 `newBlockForm` / `newTaskForm` 生成的 HTML 里
  只有 `list="people"`，那个 `<datalist id="people">` 只存在于 `editor()` 的模板里，
  且新建表单渲染时编辑器那一屏已被替换掉 ⇒ 引用悬空。修法二选一（实现者定）：
  ① 新建表单的 HTML 里也带上 `<datalist>`；② 把 datalist 提到页面级、与具体表单解耦（**倾向这个**，
  一次渲染、三处复用，且不会随表单切换而消失）。
- **显示 label**（**假定**：用户未答，取推荐项）：`<option value="<id>">` 的**文本**给
  `label`（没有 label 就退回 id）。datalist 的候选文本本来就是给认的，id 仍作为提交值。
- **可自由输入**：仍是 `<input list="…">`（不是 `<select>`），白名单只作建议 ——
  沿用现状，不把画布变成「必须先登记才能派活」。
- **候选为空时**不报错：输入框照常可用（计划可能一个参与者都没有）。

### 5.2 单一保存（Bug ②）

- **删掉 `#setst`（「改状态」）按钮**，`保存字段` 改名为「保存」（或保留「保存」二字）。
- **保存 = 字段 + 状态一起提交**（**假定**：用户未答，取推荐项）。实现口径二选一，
  以「不新增第二份实现」为准：
  - **倾向**：给 `edit` op 增加一个**可选** `status` 字段；`serve._apply` 在同一个 `plan` dict 上
    先做字段写入（`edits.edit_block`）、再做状态写入（`edits.set_status`），**成功后一次 `commit()`**。
  - 或者：前端按需发 `status` op，并**扩展它**也收 `title` / `doc` / `kind`。
  - **无论选哪条**：状态写入必须仍走 `edits.set_status`（唯一的状态机实现），
    字段写入必须仍走 `edits.edit_block` / `edits.set_field`。**不许在 `serve.py` 里重写这两段语义。**
- **「打回重做」保留为独立按钮**，行为不变（`status=claimed` + note 落 `feedback`）。
- **只提交真的动过的字段**：前端记录初值，保存时只发有变化的键；后端沿用 `edit_block`
  「只改非空」的语义。**不许**把空串当成「清空」发出去（`edit_block` 对 `""` 是「没给」，
  与命令层 `set_field` 的「空串 = 清空」不同 —— 这是既有分工，别在画布上混用）。
- **`--by`（在做）只在状态收它的时候发**：`edits.BLOCK_SET_FLAGS` 那张表是唯一约束
  （在途状态才收 `--by` / 线程三件套，`--artifact` 只在 `done`）。前端或 `_apply` 要**按目标状态
  决定发不发 `--by`**，不能把「在做」框的值无脑塞进 `set_status` —— 否则选 `pending` / `done` 之类
  会撞 `check_set_flags` 退 2。撞上时给人话错误（现状已经会打印「它收 […]」）。
- **没有变化 ⇒ 提示「没有变化」**，不发无效写入（`edit_block` 无变化时本来就返回空 changed）。
- **失败不写**：任一子步骤抛 `PlanError` ⇒ 不 `commit()`，整个请求回 400（既有语义，别破坏）。

### 5.3 边界与不回归

- **不动 `plan.json` 结构**，不加键、不改 schema（R-19 的 `BLOCK_FIELDS` 也不动）。
- **CLI 面完全不动**：`block set_status` / `set_title` / … 与 `task *` 的输出、退出码逐字节不变。
- **`docs/canvas-sync.md` 要跟着改**：op 表里 `edit` 的「还要给」加上可选 `status`，
  并写清「一次请求仍是一次 commit」「字段与状态一起提交时的语义」。
- **`REQUIREMENTS.md`**：把这两条并入（新增 R-24，或挂到 R-02 的现状列 —— 由实现者按仓库纪律选），
  改「现状」列而不是新开一份清单。
- **`README.md` / `docs/architecture.md`**：若新增了 `specs/` 目录，按仓库惯例在文档地图里加一行引用
  （否则 `.skillweave` 体检会把本文档报成「到不了根」）。
- **不碰的东西**：`plan.html`（只读看板）除非它也有同样的下拉 bug（**实现者顺手核一下**：
  `plan.html` 是只读的，按 R-02 它不该有编辑器，但若它有同样的「参与方只有 id」显示，可一并修显示）。

## 6. Testing Decisions

**测什么（外部行为，不测实现细节）**

- **候选集合**：给定一份 `participants` 只含 A、但块 owner 是 B 的 plan，`GET /api/plan` 的
  参与方候选**必须同时含 A 和 B**（这是 1a 的回归判据）。
- **新建表单**：`newBlockForm` / `newTaskForm` 渲染后，`#n_owner.list` **必须非 null**，
  且候选数 > 0（这是 1b 的回归判据）。
- **label**：候选里某一项的显示文本 = 该人的 `label`（没有则 id）。
- **单一保存**：一次保存同时改 标题 + 状态 ⇒ 回读 `plan.json`，两者**都**变了，
  且状态变更在 `runs` 里留了一条（这是 ② 的回归判据）。
- **无静默丢弃**：改了标题 + 改状态，标题**不许**丢。
- **打回**：点「打回重做」⇒ 状态回 `claimed`、note 进 `feedback`、`owner` 不变。
- **失败不写**：给一个非法状态 ⇒ HTTP 400，且磁盘 `plan.json` 的 sha **不变**。
- **CLI 不回归**：`block set_status` / `set_title` 等对同一份数据的前后输出**逐字节相同**。

**在哪测（seam 尽量高，尽量少）**

- **首选既有 seam**：画布协议 `POST /api/plan` + `GET /api/plan`（`docs/canvas-sync.md` 定义的那两条）。
  所有后端行为都能在这一个 seam 上测完，**不新增 seam**。
- **前端（DOM）测**：起 `python3 -m loomerto --plan <测试文件> open --port N`，
  用真浏览器（或 CDP）读 DOM —— 这是仓库既有先例（`docs/architecture.md` §「画布/前端改动要在真浏览器里真拖一次」，
  2026-10-07 那轮就是靠它抓到两个只在浏览器里现形的 bug）。**必须真起服务、真读 DOM**，
  不许只看 diff。**改页面资产不用重启服务**（每次 `GET /` 从磁盘重读）；改 `serve.py` 必须重启。
- **先例**：`docs/architecture.md` 的验收四道闸；`blind-tests/` 的判官法不适用（那是 description 路由盲测）。

**测试数据**：用一份**故意不登记 owner 的 participants** 的 plan（如 `skillweave` 那份的形状，
或现造一份 3 块的小 plan），因为只有这种数据才照得出 1a。

## 7. Out of Scope

- **不改 `plan.json` 结构 / schema**；不做数据迁移。
- **不新增 CLI 命令、不改任何 CLI 旗标**（R-23 的命令面保持原样）。
- **不做参与方的增删改**：画布上仍然不能「新建参与方」或「改 label」（那要改 `plan.json` 的
  `participants`，走命令层 `plan new --owner` 那条路）。本次只让**已有的**人能选。
- **不做「删块 / 删任务 / 改依赖接线」**（R-02 的「故意不做」不变）。
- **不改状态机本身**：状态集合、`STATUS_OWNER` 三档、`BLOCK_SET_FLAGS` 那张表都不动。
- **不引入前端框架 / 构建步骤**：仍是单文件内联 JS。
- **不做自动重试 / 自动合并**（`rev` 冲突仍回 409 让人刷新）。

## 8. Further Notes

- **主因是「候选来源太窄」，不是「datalist 坏了」**：`dream-waveA` 那份能正常列出 3 个候选，
  容易让人误判成「功能是好的」。回归测试**必须**用一份 owner 不在 participants 里的 plan。
- **`op=status` 静默丢 title/doc/kind 是本次的隐性缺陷**：它不只是「按钮重复」，
  而是「用户以为保存了、实际没保存」。合并保存时**必须**把它修掉，否则 bug ② 只修了皮。
- **前端 `fields()` 目前把 `by` 当成「在做」的值**（`f_by`），它同时被当作 `set_status` 的
  `--by` 和 API 的 `by`（actor）—— 实现时要**分清这两个身份**：actor（谁在改）与 `--by`（谁在做）
  不是一回事，现在撞在一起了。合并保存是修这个的好时机。
- **opencode 默认模型**已设为 `opencode-go/deepseek-v4-flash`（`~/.config/opencode/opencode.json` 的
  `model` 字段）。实测：该标识符回 `PONG`；`opencode/deepseek-v4-flash` 那个 provider 报
  `Insufficient account funds`（**别用**）。
